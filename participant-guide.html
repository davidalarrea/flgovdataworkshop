01 · The session

How this works

Here's the thing about a modern Genie: it almost always answers, and it answers confidently. On most of these questions it's right even on raw tables. The risk isn't that Genie fails — it's that on an undefined business term, a Florida-specific rule, or an internal code system it hands you a confident, plausible, wrong number you can't catch by eye. Round 1: ask the questions raw and find where Genie is confidently wrong. Round 2: add context so every answer is governed, consistent, and trustworthy. We build Spending together; you keep all three datasets.

  1. Load one dataset into your workspace using a ready-made notebook (§02).
  2. Build a Genie agent over its tables (§03).
  3. Round 1 — ask the questions with no context. Most land. A few come back confidently wrong. Learning to spot which is the point.
  4. Round 2 — add context (column & table descriptions, Genie instructions, and metric views), then re-ask and watch the wrong answers become governed and correct.

03 · Stand it up

Build a Genie agent

A Genie agent lets you ask questions of your tables in plain English. Point it at the three tables you just loaded and start with Round 1 — before adding any context.

  1. In the left sidebar, open Genie and click New.
  2. Choose the three tables in your schema — fl_gov_demo.spending (or .health / .transportation).
  3. Pick your SQL warehouse and create the agent.
  4. Go straight to Round 1 — ask the questions in the dataset sections below with no context yet.

Your four tools for adding context

In Round 2 you'll fix the failing questions with these four levers. Match the tool to the miss:

ToolFixes…Where
Column descriptionInternal codes Genie can't decode (FLAIR object codes, FDOT districts, fund groupings)Column comment (Catalog Explorer) or the agent's Instructions / Knowledge

Where you add it matters
A decode you add as a Genie instruction improves Genie's written answer — but the chart axis still shows the raw code. Setting the column comment in Catalog Explorer propagates the decode into chart labels and every downstream tool. For coded dimensions you'll chart (agency, district, category), set the catalog column comment, not just a Genie instruction.

Round 2 · step 2 — Genie instructions

Genie agent → Configure → Instructions → paste as general instructions:

- Fiscal year means the Florida state fiscal year, July 1 to June 30, named for the year it ends. FY2026 = 2025-07-01 through 2026-06-30. Derive it from payments.pmt_dt.
- A payment is late under the Florida Prompt Payment Act (s.215.422) when payments.pmt_dt is more than 40 days after payments.invoice_dt. On time = 40 days or fewer.
- A potential duplicate payment is two payments with the same vendor_id and pmt_amt, different pmt_id, made within 3 days of each other.
- Split purchasing = 3 or more contracts to the same vendor_id, each with contracts.contract_amt under $35,000 (the Category Two threshold), executed within 30 days of each other.
- Spend always means payments.pmt_amt, never contracts.contract_amt.

Round 2 · step 3 — metric view

Create fl_gov_demo.spending.payment_metrics (paste-ready SQL in the metric-views appendix), then add it to the agent as a data source.

Takeaway
Every “Wrong” answer above looked authoritative — Genie confidently applied the federal fiscal year, Net-30, and its own duplicate rule. Three layers fix it: column descriptions (decode the codes), instructions (the rules), and one metric view that pins the fiscal year, the 40-day rule, and the state/federal grouping so every answer — and every dashboard tile — agrees.

Round 2 · step 2 — Genie instructions

Genie agent → Configure → Instructions → paste as general instructions:

- When asked for the worst, highest, or lowest mortality, rank counties by the age-adjusted death rate (county_mortality_metrics.age_adjusted_death_rate_per_100k), not the crude rate.
- Follow the NCHS reliability standard: do not rank or report a rate whose numerator is fewer than 20 events; label it statistically unreliable instead.

Round 2 · step 3 — metric view

Takeaway
Genie's arithmetic was right every time. What it lacked was methodology: age-adjust before ranking, and suppress rates built on fewer than 20 events. Pin the method in a metric view and an instruction, and every analyst gets the same governed rate.

Appendix A · Round 2 deep-dive

Metric views

Paste-ready governed measures for the questions where the method matters — age-adjusted mortality and net-of-deobligation funding. Define the measure once as a metric view and it computes the same agreed way everywhere: Genie, dashboards, and SQL.

How to create one

Two ways — UI or SQL

A metric view is a Unity Catalog object that defines dimensions (grouping columns) and measures (aggregate expressions like a rate) over a source query. Prerequisite: a SQL warehouse or cluster on Databricks Runtime 17.3+.

  1. UI builder. In Catalog Explorer, open a table → Create → Metric view. The editor opens with a visual (UI) tab and a YAML tab — two views of the same definition; add dimensions and measures in either.
  2. SQL. Run a CREATE VIEW … WITH METRICS LANGUAGE YAML statement in the SQL editor or a notebook — the templates below.
  3. In your Genie agent, add the metric view as a source so rate questions resolve to the governed measure instead of a raw count.
YAML keys
version, source (a SELECT), optional joins / filter, fields (dimensions), and measures (aggregates). Each measure is an aggregate such as SUM(a) / SUM(b), so the rate stays correct at any grouping — statewide or per-county.

Spending · the live build

payment_metrics

One governed view over payments ⋈ contracts (many-to-one, so no fan-out). It pins three rules raw Genie gets wrong — the Florida fiscal year, the 40-day Prompt Payment Act clock, and state vs. federal fund grouping — and decodes agency names for chart labels.

CREATE OR REPLACE VIEW fl_gov_demo.spending.payment_metrics
WITH METRICS LANGUAGE YAML AS $$
version: 1.1
source: |
  SELECT p.pmt_id, p.pmt_amt, p.pmt_dt, p.invoice_dt, p.fund_src, c.agency_cd
  FROM fl_gov_demo.spending.payments p
  JOIN fl_gov_demo.spending.contracts c ON p.contract_id = c.contract_id
fields:
  - name: agency
    expr: |
      CASE agency_cd
        WHEN 'DOT' THEN 'Transportation'       WHEN 'DOC' THEN 'Corrections'
        WHEN 'DCF' THEN 'Children & Families'  WHEN 'DOH' THEN 'Health'
        WHEN 'DEP' THEN 'Environmental Protection'
        WHEN 'DMS' THEN 'Management Services'  WHEN 'DOR' THEN 'Revenue'
      END
  # Florida fiscal year runs Jul 1 - Jun 30 and is named for the year it ends
  - name: fiscal_year
    expr: YEAR(pmt_dt) + CASE WHEN MONTH(pmt_dt) >= 7 THEN 1 ELSE 0 END
  - name: fund_category
    expr: CASE WHEN fund_src IN ('GR','TF') THEN 'State' ELSE 'Federal' END
measures:
  - name: total_spend
    expr: SUM(pmt_amt)
  - name: payment_count
    expr: COUNT(pmt_id)
  # FL Prompt Payment Act (s.215.422): late = paid more than 40 days after invoice
  - name: late_payments
    expr: SUM(CASE WHEN DATEDIFF(pmt_dt, invoice_dt) > 40 THEN 1 ELSE 0 END)
  - name: prompt_pay_compliance_pct
    expr: 100.0 * SUM(CASE WHEN DATEDIFF(pmt_dt, invoice_dt) <= 40 THEN 1 ELSE 0 END) / COUNT(pmt_id)
$$;
Try it
Ask S16 (“prompt-payment compliance by agency in FY2026”) before and after adding the view. Raw: Net-30 over the federal year (~76% overall). Governed: 99.1–99.8% by agency. The same view also fixes S10, S11, and S12.

Health · governance showcase

county_mortality_metrics

The age-adjusted death rate via direct standardization: each age band's death rate, weighted by the US-2000 standard population, summed — so age structure no longer confounds the ranking. The standard weights live inside the view, which is why raw Genie can only give a crude rate.

CREATE OR REPLACE VIEW fl_gov_demo.health.county_mortality_metrics
WITH METRICS LANGUAGE YAML AS $$
version: 1.1
source: |
  WITH stdw AS (
    SELECT * FROM VALUES ('0-17',24600),('18-44',39600),('45-64',19600),
                         ('65-74',8300),('75+',7900) AS t(age_group, std_pop)
  )
  SELECT d.county_nm, d.yr, d.age_group, d.deaths_n, p.pop, s.std_pop
  FROM fl_gov_demo.health.deaths_by_age d
  JOIN fl_gov_demo.health.population p
    ON d.county_nm = p.county_nm AND d.yr = p.yr AND d.age_group = p.age_group
  JOIN stdw s ON d.age_group = s.age_group
fields:
  - name: county
    expr: county_nm
  - name: year
    expr: yr
measures:
  - name: age_adjusted_death_rate_per_100k
    expr: SUM((deaths_n * 1.0 / pop) * std_pop)
  - name: crude_death_rate_per_100k
    expr: SUM(deaths_n) / SUM(pop) * 100000
$$;
Try it
Ask H11 (“worst mortality in 2024”) before the view (crude → Hamilton, Gadsden, Hendry) and after (age-adjusted → Bay, Gadsden, Columbia).

FDOT / Transportation

capital_program_metrics

Net obligated (deobligations subtracted), expenditure rate, and unobligated balance as governed measures. The oblig_type sign convention is baked in so no one double-counts a released obligation.

CREATE OR REPLACE VIEW fl_gov_demo.transportation.capital_program_metrics
WITH METRICS LANGUAGE YAML AS $$
version: 1.1
source: |
  SELECT o.oblig_id, o.fund_src, o.fy, o.auth_amt, o.oblig_amt, o.expend_amt,
         o.oblig_type, p.dist_no, p.proj_type, p.status_cd
  FROM fl_gov_demo.transportation.obligations o
  JOIN fl_gov_demo.transportation.projects p ON o.proj_id = p.proj_id
fields:
  - name: district
    expr: dist_no
  - name: fund_source
    expr: fund_src
  - name: fiscal_year
    expr: fy
measures:
  - name: authorized
    expr: SUM(auth_amt)
  - name: obligated
    expr: SUM(CASE WHEN oblig_type = 'DEOBL' THEN -oblig_amt ELSE oblig_amt END)
  - name: expended
    expr: SUM(expend_amt)
  - name: expenditure_rate
    expr: SUM(expend_amt) / SUM(CASE WHEN oblig_type = 'DEOBL' THEN -oblig_amt ELSE oblig_amt END)
  - name: unobligated
    expr: SUM(auth_amt) - SUM(CASE WHEN oblig_type = 'DEOBL' THEN -oblig_amt ELSE oblig_amt END)
$$;
Try it
Ask T09 (“total obligated funding”) before ($9.89B, gross) and after ($9.71B, net of deobligations).

Appendix B · if time allows

AI/BI dashboards

Turn your agent's tables into an AI/BI dashboard — built entirely by asking Genie, no SQL. Each dashboard opens with a row of KPI tiles, then charts. The rate-based tiles reuse the same metric views you defined for Genie — context, once defined, powers both.

How to build it

Build it with Genie

You won't write a line of SQL. Ask Genie each question in the tables below, then turn its answer into a dashboard tile. Everything runs on serverless — there's no warehouse to pick.

What these prompts assume

The prompts below assume you've already done Round 2 for your dataset — the same context that makes Genie's written answers trustworthy makes the dashboard tiles trustworthy. Without it, Genie still answers, but it charts a confidently wrong number, not an obvious error. Build the context first (in the dataset sections above), then build the dashboard:

  1. Dataset loaded & agent set up. The §02 notebook has run and your §03 Genie agent points at the three tables.
  2. Column comments are set. They decode the codes and propagate into chart axis labels — so a bar grouped by agency, district, or category reads in plain English, not agency_cd values (§03 — “Where you add it matters”). A Genie instruction alone fixes the written answer but leaves the axis showing raw codes.
  3. Genie instructions are in place. The business rules Genie can't guess — Florida fiscal year (Jul–Jun), the 40-day Prompt Payment clock, what “active” means, approved-only change orders, net-of-deobligation — must be stated, or tiles like “spend by fiscal year” and “change-order % by type” chart the wrong figure.
  4. Metric views are added to the agent. The health age-adjusted map and the FDOT net-obligated / expenditure-rate tiles only compute correctly if you've added the Appendix A metric view — otherwise Genie falls back to the raw (crude / gross) number.
  1. Ask Genie a question from the tables below. It answers and renders a chart.
  2. Not the chart you wanted? Tell it (“make it a bar chart”) or switch the visualization type on the result.
  3. Click ⋮ → Add to dashboard. The first one creates the dashboard; after that, add each new tile to the same one.
  4. Repeat, then arrange. Open the dashboard, lay out the tiles, add the filters listed per dataset, and toggle Draft → Published to share a read-only copy.
